# CC_Problema

> Punto de partida de todo proyecto. Su resolución determina el propósito del proyecto — hay que definirlo bien para no malgastar tiempo ni recursos.

## Esquema básico

```
CAUSAS → PROBLEMA → EFECTOS
```

Para identificar un problema hay que identificar sus **causas** y sus **consecuencias**. Se puede usar un **árbol de problemas** como herramienta.

## Qué NO es un problema

- Una app / página web / plataforma
- Un producto
- Una solución tecnológica
- Un bot

Todo eso ya es una **solución**. Si tu punto de partida es "quiero hacer una app que...", todavía no tenés el problema.

## Preguntas para describirlo bien

- ¿Existe realmente el problema?
- ¿Cuál es el problema?
- ¿Cuáles son sus elementos esenciales?
- ¿A qué población afecta?
- ¿En qué zona geográfica está?
- ¿Cuáles son sus causas y consecuencias?
- ¿Qué pasa si se resuelve?
- ¿Qué magnitud tiene?

## Cómo se redacta

- Se plantea como **hipótesis**: un suceso con impacto negativo o consecuencias no deseadas
- Oraciones **cortas y objetivas**, con datos reales si los hay
- **No incluye la solución**, ni asunciones, ni prejuicios sobre causas/efectos
- La hipótesis se refuta o confirma después, con investigación (encuestas, entrevistas, papers)

## Estructura simple para definirlo

```
[Usuario específico] tiene el problema de [situación concreta]
cuando [contexto], lo que genera [impacto negativo].
```

**Ejemplo:**
> Estudiantes de primer año tienen el problema de olvidar fechas de entrega cuando usan múltiples plataformas, lo que genera estrés y bajo rendimiento académico.

## Características de un buen problema (para MVP)

| Característica | Mal ejemplo | Bien |
|---|---|---|
| **Específico** | "La gente pierde tiempo" | "Estudiantes universitarios pierden tiempo organizando entregas en múltiples plataformas" |
| **Relevante** | — | Genera frustración, costo o ineficiencia real |
| **Validable en corto plazo** | — | Se puede testear con usuarios reales en ~2 meses |
| **Enfocado** | "Todos" | Un segmento de usuario concreto |

## Relación con el MVP

Un [[MVP]] no busca construir el producto completo — busca validar:
1. Si el problema existe
2. Si alguien realmente quiere resolverlo
3. Si la solución propuesta tiene sentido
